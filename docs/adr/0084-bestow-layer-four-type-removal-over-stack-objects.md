# Bestow is a CR 613 layer-4 continuous effect, and the layer system grows to cover objects on the stack

## Status

proposed

## Context

Bestow (CR 702.103, issue #703 — Springheart Nantuko, Detective's Phoenix) is
an alternative cost that **changes what the object is**. Cast for its bestow
cost, an enchantment creature card:

- becomes an **Aura spell** on the stack and gains "enchant creature"
  (CR 702.103a) — so it targets, and it is no longer a creature spell;
- enters attached to that creature, as an Aura enchantment that **is not a
  creature** (CR 702.103b);
- when it becomes unattached, **stops being an Aura and becomes a creature
  permanent** rather than being put into its owner's graveyard
  (CR 702.103c/704.5m).

Two properties of the current engine bear on how that is expressed:

1. `StackItem.types` and `CardInstanceState.types` are **stored, mutable
   arrays**, read by every consumer of an object's types — the spell-target
   filters (`gre/targetFilters.ts`), the creature-spell mana restriction, the
   trigger scans, SBA creature-ness, and ~4 client sites in
   `src/lib/card-utils.ts`. Overwriting them is therefore the cheapest possible
   implementation, and there is precedent: face-down (ADR 0013) and transform
   (ADR 0067) both mutate stored characteristics in place, explicitly to avoid a
   new "effective card" seam.
2. The layer system (`gre/layers.ts`, CR 613) does type/subtype **add** at
   layer 4, but has **no type removal**, and applies only to battlefield
   permanents — `PermanentView` is assumed throughout.

The tempting move is to follow the precedent: stamp `bestowed`, overwrite
`types` to `["Enchantment"]` on the stack and on the battlefield, restore them
from the definition on unattach. It works, it is small, and every existing
reader sees it for free.

## Decision

**Bestow is implemented as a real CR 613 layer-4 continuous effect, and the
layer system is extended to apply to objects on the stack. The stored-mutation
shortcut is rejected.**

The distinction that decides it is a CR one, not a taste one:

| CR category                                        | Right mechanism                            | Examples                                   |
| -------------------------------------------------- | ------------------------------------------ | ------------------------------------------ |
| **Copiable values** (CR 706/708.2/712)             | mutate stored characteristics              | face-down (ADR 0013), transform (ADR 0067) |
| **Continuous effect from an ability** (CR 611/613) | the layer system, recomputed at every read | bestow (CR 702.103a), anthems, Humility    |

Face-down and transform change what the object's copiable values _are_ — that
is what a copiable value is, and storing it is correct. Bestow's type change is
not a copiable-value change: it is a continuous effect generated by the bestow
ability, sitting in **layer 4**, and CR 613.1 requires it to be recomputed
whenever the characteristic is checked. ADR 0013 and ADR 0067 are therefore
**not** precedents for it, and this ADR exists partly to stop them being cited
as such for the next effect of this shape.

So this decision adds two capabilities:

**1. Layer-4 type REMOVAL.** Layer 4 today only adds types/subtypes. Bestow
requires removing `Creature` (and adding `Aura`) while attached. Removal joins
the existing layer-4 vocabulary rather than becoming a bestow-specific hook, so
"loses all creature types", "is no longer a creature" and the rest arrive with
it.

**2. The layer pipeline applies to objects on the stack.** CR 613.1 governs
_objects_, not just permanents; a bestow spell is an Aura spell **while on the
stack**, which is what makes it counterable as an Aura spell, illegal to target
with "target creature spell" effects, and invisible to "whenever you cast a
creature spell". `PermanentView` generalises to an object view so the same
layer evaluation answers for a stack item.

The bestow effect itself is declared, not hardcoded: the `getDefinition` seam
expands the `bestow` keyword (the `expandHideaway`/`expandFadingVanishing`
pattern, ADR 0054) into the layer-4 effect, gated by an `applies` predicate
reading the instance's `bestowed` flag — so the keyword can never be printed
with nothing enforcing it (the deathtouch/hexproof inertness shape Guard A
exists to catch), and bestow's rules text lives in exactly one place.

CR 704.5m gets its bestow arm in `gre/sba.ts`: a hostless permanent whose
`bestowed` flag is set clears the flag and stays on the battlefield (whereupon
the layer-4 effect stops applying and it reads as a creature again) instead of
being put into its owner's graveyard.

**Sequencing against ADR 0082.** PRD #2064 is migrating every layer into one
Continuous Effects Registry, and its slice **S4** covers layers 2–5 (control,
text, **type**, colour). Bestow's type removal and the stack-object path are
built in today's `gre/layers.ts` — an extension of the single existing model,
not a second one — and migrate wholesale at S4, which is recorded as known
scope on that slice. Blocking bestow on an unstarted 8-slice PRD was rejected:
the CR-faithfulness at stake is about the **mechanism** (derived continuous
effect, never stored mutation), which this delivers now; the registry is about
_where the one authority lives_, which S4 fixes for every layer at once.

## Consequences

Positive: the first correct layer-4 type-removal in the engine, available to
every "stops being a creature" / "loses all types" effect after it; spell
characteristics stop being a mutable array that any cast path may overwrite;
bestow's unattach behaviour falls out of the effect ending rather than needing a
restore-from-definition routine that could drift from the printed card.

Negative: materially more work than the shortcut — the stack-side readers
(~11 non-test sites across `gre/state.ts`, `gre/targetFilters.ts`,
`gre/replacements.ts`, `cards/filters.ts` and `src/lib/card-utils.ts`, the last
of which is **client** code) must move from reading `item.types` to asking the
layer pipeline, and the pipeline runs inside the bot's cloned-state search, so
the per-read cost is on a hot path (PRD #2064's S7 perf pass inherits it).

Divergence, deliberate: CR 613.8 dependency ordering is not implemented for
these effects any more than for the existing ones — tracked in #2068. With a
single stack-side type-changing effect in the pool, layer+timestamp ordering is
trivially correct; a second one lands on the registry, not on this code.
